Design considerations (Ledgerline is a fictional product; this concept is about the pattern, not a specific app)

  • Context fragmentation. A new tab per click removes the trail of breadcrumbs. In-place navigation keeps the user's place in the hierarchy visible (see the breadcrumbs in Proposed mode).
  • State disconnects. Each tab holds its own copy of the data. In Today mode, open the same customer in two tabs and toggle its status in one: the other goes stale. Avoiding that across tabs needs extra sync work (WebSockets, storage events).
  • Execution friction. Count the tabs after a short task, then use “Tab triage” to see the clean-up cost users pay at the end of the day.
  • Browsers limit “replace and close”. window.close() generally works only on windows opened by script, so closing the previous tab is unreliable. Single-window routing achieves the same outcome without it.
  • Context kept in place. The invoice opens in a slide-over drawer, so the order underneath stays visible and “back” is one click.
  • Deep links. The URL hash updates on every step, so Back, Refresh and bookmarks work. A real build would use real routes (for example React Router or Vue Router).
  • Unsaved work. In-place navigation can discard edits. Edit a Settings field, or tick “Simulate unsaved work”, then navigate in Proposed mode to see the guard. design requirement
  • Some new tabs are deliberate. Exports, print views, external links and side-by-side comparison are better as an explicit “open in new tab” action. Scope this change to routine drill-down.
  • Not measured. Tab counts here are simulated. Memory use, load times and real-user effort are untested.
